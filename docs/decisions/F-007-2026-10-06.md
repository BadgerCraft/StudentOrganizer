# F-007 / DEC-003 — Private, deliberate bug receipt

Research/inspection: October 6, 2026. Decision packet only; no receiver adopted, account created, hosting provisioned, report sent, or credentials requested. Source: PR #13 `a6dd17365d3b474e50393dad3da64f1df74708ee`; PR #15 `a77fe406105f4153f9cb70f5c8af458fb0bee1aa`. Reporting service and modal are identical across these heads.

## Actual behavior and data
The app saves one editable report in localStorage key `ota.bug-report-draft.v1`, separate from classroom IndexedDB and absent from classroom backups. Fields are schema version 1, random report UUID, summary, steps, expected, actual, app version, hexadecimal build SHA or `unknown`, coarse platform, allowlisted screen, and optional edited preview. Each input is limited to 2,000 characters; edited preview to 12,000. Summary/actual are required for preview. Users can remove metadata in that complete editable preview. Copy/download contain exactly that preview and explicitly say they have not sent it. There is no Send button, configured central endpoint, or reporting network call.

No record, teacher/student identity, grade, note, raw URL, screenshot, photo, full user agent, stack trace or database attachment is automatically included. Text users type may still contain private information; review/reminder is necessary. Unreadable stored drafts remain until explicit replacement; storage/copy/download errors are visible. Local drafts and downloads are not confirmed receipt.

## Exact boundary if receiver implementation is later authorized
Send only the complete edited preview text plus an opaque report ID disclosed separately in preview if used for receipt/deduplication; no hidden metadata. Show provider/destination before explicit Send. No automatic attachments/background send/retry; classroom network deny rules must remain intact except a narrowly authorized reporting route. Native iPad currently denies external web traffic: merely adding an endpoint must not weaken that boundary. Maintain draft on offline/cancel/quota/CAPTCHA/timeout and unknown-delivery outcomes; request initiation or a generic success UI is not proof of receipt. Verify a fictional report ID in the private receiver, then manually sanitize any public ledger entry. Provider sees connection metadata such as IP/time even when app payload is minimal; no promise of anonymous network use.

Tyler's consequential choice: **use a named existing private channel for the manual pilot, or authorize a new private account-free receiver such as Formspree?** Approval of a provider would authorize only bounded receiver setup/transport investigation under the selected free plan, with explicit account ownership/access supplied securely; no paid upgrade, student data, general hosting, merge or release. Implementation/access scope should be recorded precisely before transmitting anything.
