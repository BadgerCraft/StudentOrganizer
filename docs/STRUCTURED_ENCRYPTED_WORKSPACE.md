# Structured encrypted workspace contract

This development engine preserves the reviewed AEAD and chunk v1 formats. It changes the encrypted working payload into immutable logical objects and bounded encrypted metadata. It does not activate encryption, configure a credential, or establish packaged-device acceptance.

## Objects and publication

`electron/structuredWorkspace.cjs` exposes `StructuredWorkspace.create/open`, `commitDelta(expectedRevision, changes, assertCurrent)`, `list`, `readRecord`, `readRecordStream`, `readSelected`, `readAll`, `restoreCheckpoint`, `getRevision`, `getRecoveryWrapperHash`, and `lock`. The main process owns the key, scope, recovery-wrapper hash, stores, and context guard. Never accept those dependencies or authorization flags from a renderer payload.

A change is `{namespace, table?, key, value}` or `{namespace, table?, key, deleted:true}`. Namespaces are `primary`, `recovery`, `storage`, and `metadata`; only primary/recovery have a table. The identity is the canonical JSON tuple `[namespace,table-or-empty,key]`. `studentOrganizerRecords.cjs` maps the supported complete bundle to these records and back, retaining empty table markers, binary IndexedDB primary-key order, and exact historical backup/storage strings. Dated backups split into a `recovery/backups` metadata record and paired `recovery/backup-content` exact JSON-string body. `bundleFromRecords` requires both; `bundleViewFromRecords` accepts metadata without bodies and returns `{bundle,backupCatalog}` with no fabricated backup JSON. The view bundle has an empty backups array; its catalog is separately authenticated metadata, not a complete export. `recordChangesFromLegacyDelta` expands full legacy backup additions/deletions into both logical records. Native full export/restore must explicitly load and validate the body. Mapping is not schema, byte, or permission validation.

Each object uses `working-data` AEAD with a record ID comprising the tuple hash and a fresh UUID. SQLite/envelope metadata is public; it contains opaque identifiers and ciphertext sizes, never student names or filenames. Logical keys and refs appear only in encrypted metadata. Unchanged object contents reuse authenticated immutable refs; only changed objects and their metadata shard are rewritten. The unreleased private SO root payload is version 2; existing version 1 payloads remain readable and upgrade on their next write. Version 2 authenticates `objectRevisionCeiling` separately from this computer’s protected root revision. Immutable refs are bounded by this ceiling, while each local checkpoint still advances exactly by one. Ordinary edits preserve `max(existing ceiling,next local revision)`. This is app metadata, not a change to shared AEAD/chunk formats or the protected-head protocol.

The encrypted root authenticates the record count; deltas enforce the global two-million-record ceiling and listing checks count closure. At most 256 hashed-key metadata shards (8 MiB/8192 entries each) are referenced from a root of at most 16 MiB. No whole-bundle JSON encoding occurs on a delta commit.

Records serialize as streamed JSON fragments and 4 MiB plaintext chunks, with per-record measurement/hash before publication. Each chunk store object and final authenticated seal must be durable before an encrypted root CAS makes it current. Failed or uncertain root publication locks the session and requires readback/reopen; it never retries an uncertain write. Staged and old ciphertext objects remain retained. There is no automatic garbage collection, disk-space reclamation, or whole-store rollback protection from this layer alone. The native checkpoint/protected-head provider supplies its separate durability and rollback contract.

Confirmed native restore may call `restoreCheckpoint(expectedRevision, historicalCheckpoint, safetyIdentity, guard)` after a main-pinned preview and authority check. It authenticates the retained root under the same app/vault/key/wrapper hash, rejects source revisions/ceilings beyond the already authenticated ceiling, verifies the current durable root matches cached state, and republishes the historical immutable refs at **current revision + 1**. In the same root commit, it creates a fresh encrypted `metadata/internal-safety/<uuid>` record containing the exact pre-restore root checkpoint and creation time. The caller supplies only the safety identity, never safety contents. Reversing that restore uses the retained checkpoint and another increasing revision, without loading every historical body. Root safety controls are outside the legacy data bundle; no OS head reset or ciphertext deletion occurs. This primitive authenticates the retained root and its modified safety shard; it does not prove availability or byte integrity of every other referenced object. Before a fully verified restore commit, the native preview must iterate all selected-root user records and histories for canonical byte validation and authority without collecting them into one aggregate allocation. Missing/corrupt bodies fail closed. Engine integrity does not replace native confirmation, pinned-token freshness, or full historical authority checks.

Explicit archive adoption is separate from ordinary restore. `StructuredWorkspace.importAuthenticatedCheckpoint(options,sourceCheckpoint,guard)` opens a **fresh** local root at revision 1; the instance method `importAuthenticatedCheckpoint(expectedRevision,sourceCheckpoint,safetyIdentity,guard)` advances an existing local root to M+1 with its exact old root retained atomically. Both authenticate the source scope/wrapper and retain its immutable refs under `max(source ceiling,current ceiling,new local revision)`. Thus source revision 8 can be adopted locally at 1 without rebasing every encrypted object or jumping/resetting the OS ledger. `getObjectRevisionCeiling()` is main-only context for source-control bounds. The caller must fully verify the source archive, all bodies, schema and ownership, pin the native preview token and require the existing confirmation/enrollment proof before invoking this method. An authenticated source root alone is not a completed authorized import.

The encrypted root authenticates the main-owned recovery-wrapper hash. Delta changes cannot replace it. A wrapper selected for backup export must match this authenticated hash. Full workspace authority applies at conversion/export/recovery replacement; ordinary internal persistence preserves existing teacher/service permissions rather than adding a new administrator requirement.

## Memory and read boundaries

The protocol object ceiling is 128 GiB, inherited from the existing chunk format; this is a planning ceiling, not a claim of actual 128 GiB JSON hydration or device IO acceptance. Writes avoid whole-bundle strings and arrays of all encoded plaintext. Callers still supply one already-materialized logical record; capture media must not be represented as an enormous in-memory JSON string.

`readRecord` rejects a record over 256 MiB. `readAll` preflights 512 MiB of raw record/key bytes before reading bodies and also enforces the individual limit. `readSelected(identities)` applies those same lower-only per-record and aggregate budgets to the complete requested set before reading any selected body. Its identities have exactly `{namespace,table?,key}`; duplicate, malformed or missing selections fail closed. Shard metadata is authenticated during preflight, then values materialize in requested order through the serialized read queue. Unselected historical bodies do not consume the selection budget. Native startup must use one selection containing **all** loaded primary and root-control records while excluding lazy `backup-content`, rather than individually collecting unbudgeted reads. A capacity rejection leaves the original encrypted checkpoint and source data in place; it is not permission to raise the limits or discard originals.

These are conservative raw-byte budgets, not guarantees against every JavaScript object-overhead allocation. Limits may be lowered by trusted options, never raised. Metadata listing has a separate 64 MiB key-budget guard. Read-limit failures lock the session; reopen before choosing a smaller or streamed operation.

`readRecordStream(identity, sink)` verifies/decrypts at most one shared-format chunk at a time and resolves only after full stream count, final seal, and content hash verification. Sink chunks are borrowed and wiped after callback completion. A sink must stage its output and publish it only after the promise resolves; partial output is not a completed authenticated file. Lock or context cancellation invalidates the operation. This API does not create plaintext temporary files.

The app must load primary working records and small recovery metadata, retaining dated history bodies lazily for restore/export. It must not call `readAll` to hydrate arbitrary aggregate history. Full user-requested export/readback can stream records individually. The native canonical validator iterates historical snapshots one at a time and validates already-owned primary data without serializing the whole bundle. `createMainBundleValidationCache()` supplies the native host with `initialize`, `validateCandidate`, and `clear`. Initialization returns a detached, fully verified, deeply frozen baseline. Candidate validation freezes newly owned records before its first await, always rechecks current schema/relationships, and skips expensive unchanged-file/history work only for exact object identities verified and frozen by that cache. Same IDs, claimed hashes, renderer flags, and arbitrary frozen objects receive no trust. New/changed dated backups and sync bases receive full schema and byte validation. The native host retains the authoritative current bundle and adopts a candidate only after durable root publication; the cache does not itself choose a current revision or grant permission. Clear it on lock/close/context replacement. `measureRecord` exports the same deterministic streamed JSON byte count/hash used for object publication, for main-owned migration proofs.

## Verification and limits

Synthetic SQLite tests cover aggregate bodies many times an injected per-record limit, dirty-only rewrite, history reuse, Unicode/lone-surrogate JSON, exact recovery strings, immutable tuple identity, current scope, recovery-wrapper binding, key isolation, CAS/stale writers, held publication, failed/lost acknowledgments, materialization preflight, borrowed streaming buffers and lock during streaming. Independent source review is required before integration.

Actual large-disk workloads, disk quota exhaustion, packaged Windows/Mac SQLite/OS-key behavior, real two-computer enrollment and user recovery-code acceptance remain separate gates. No real student data, live account grants, release or deployment is implied.
