# Shared encryption contract — draft v1, October 29, 2026

Implementation lives in `shared/encryption/index.ts` (bounded envelopes/recovery) and `shared/encryption/chunks.ts` (bounded chunk stream). Node 24, current Electron Chromium and secure-context browsers use established Web Crypto AES-GCM and HKDF-SHA-256, with no added dependency or new service. This draft is a reusable foundation, not a claim that either app's existing plaintext storage is converted. Consumer integration and independent security review remain required before activation.

## Wire format and key boundaries

Generate an independent 32-byte random master with `generateMasterKey()` for each app/vault. Never reuse a Student Organizer master in ServeTrack. Runtime keys are sensitive memory, never application records, telemetry, AI input or logs. Protected OS storage adapters must fail closed if unavailable or insecure; they must not fall back to plaintext or weak Linux storage. The foundation performs no persistence or provisioning.

`encryptBytes(master, context, bytes)` returns a canonical v1 JSON envelope. `decryptBytes(master, expectedContext, serialized)` returns authenticated bytes or a generic `EncryptionError`, with no partial plaintext fallback. Context is `{appId,vaultId,purpose,recordId,revision,keyVersion}`; purposes are `working-data`, `attachment`, `backup`, `transfer`, `recovery-key`. Identifiers must be opaque non-sensitive ASCII IDs (1–200 characters, letters/digits then letters/digits/`._:/-`). Revision is a nonnegative safe integer, keyVersion a positive safe integer. Do not use student names, filenames or notes as public context.

Envelope metadata binds format, version, fixed algorithm and every context field through AES-GCM additional authenticated data and HKDF info. Each encryption uses a fresh random32-byte salt, random12-byte nonce, derived non-extractable AES256 key, and128-bit GCM tag. Ciphertext uses canonical base64. Strict parsing rejects unknown fields, duplicate JSON fields, alternate serialization, unsupported algorithms/versions, malformed encoding, oversized input and missing tags. UTF-8/string encoding is the consumer's explicit choice; the primitive protects arbitrary bytes. The bounded envelope limit is128MiB plaintext, not a promise to allocate arbitrarily large recordings. No compression or algorithm negotiation is provided.

Expected context comes from trusted local state. Passing the envelope's own revision as the expected revision defeats rollback detection. A valid older envelope cannot be distinguished from a legitimate requested historical backup without the consumer's independently trusted revision/manifest. This component does not provide a server, monotonic hardware counter, forward secrecy, protection from unlocked-device malware, or guaranteed JavaScript memory erasure.

## Recovery and a second computer

`generateRecoveryCode()` creates256 random bits formatted as `TV1-` followed by eight8-hex-character groups and an8-hex-character SHA256 typo checksum. Case is accepted either way; other spelling changes fail. It is a high-entropy secret generated by the app, not a user password; the checksum adds no secret entropy. A copied recovery code must be kept offline by the user and never persisted with the vault. Screens/UI must avoid including it in diagnostic captures.

`wrapMasterKey(master, code, appId, vaultId, keyVersion)` seals the32-byte master under the recovery secret with a dedicated `recovery-key` context (`recordId=master-key`, revision0). `recoverMasterKey(...)` verifies the context/authentication and returns exactly32 bytes. Generated raw recovery byte copies are best-effort zeroed; JS strings and WebCrypto internals cannot be guaranteed wiped. Rotation/revocation and device authorization remain consumer protocols, not implicit properties of a recovery wrapper.

Before enabling conversion, the consumer must verify: the saved offline code successfully recovers the exact master; a distinct second-device adapter can import it, protect it with that device's OS storage and decrypt a fresh challenge; locked/restarted operation fails closed and trusted unlocking restores access. Never infer these from a checkbox or the existence of a wrapper. Synthetic adapters/tests do not establish actual-device acceptance. User activation remains separate.

## Large attachments and transfers

ServeTrack currently allows20GiB recordings,32GiB legacy backups and100GiB project backups, so whole-buffer envelopes alone are insufficient. `createChunkManifest(master,scope,totalBytes)` returns an encrypted manifest and plan; `openChunkManifest` authenticates it. The manifest contains a random file UUID,4MiB fixed chunk size, total bytes and exact chunk count, up to128GiB plaintext. `sealChunk` and `openChunk` bind the full original context, complete manifest and zero-based position through a derived opaque chunk record ID. Every non-final chunk is exactly4MiB; the final chunk has the exact remaining length. A fresh file UUID prevents mixing separate files with identical lengths/context.

`createChunkManifest` produces a draft plan, not a publishable complete file. After writing every encrypted chunk, `finalizeChunkManifest(master,scope,plan,source)` verifies the staged chunks and encrypts a final seal containing the ordered SHA256 digest list. This commits exact ciphertext generations, so replacing a chunk with another valid encryption for the same file/position is rejected. A128GiB file has at most32768 digests (about2MiB metadata).

`verifyChunkStream(master,scope,finalManifest,source,sink)` requires this final seal, checks each ciphertext hash before decryption/sink and verifies each chunk sequentially and rejects reordering, duplication, truncation, extra chunks, cross-file substitution and wrong lengths. Its successful completion is the full-file publication condition. Sink callbacks receive authenticated plaintext only while needed; their arrays are overwritten after the awaited callback. A sink may consume in memory or re-encrypt into encrypted staging. **Never publish an output file before the verifier resolves, and never stage plaintext temporary files.** Discard incomplete staging on failure. Consumers must honor a transaction/commit manifest or atomic rename and bound disk usage including base64 overhead (roughly4/3 plus headers);128GiB plaintext is not128GiB ciphertext.

The library does not implement filesystem staging/rename, streaming JSON export or disk quota handling. Actual20GiB/100GiB file IO, power-loss recovery and OS storage tests are separate acceptance gates. A forged/unverified plan must never be accepted as trusted manifest metadata. The API does not automatically fetch or transmit anything.

## Consumer preservation checklist

- Opt-in conversion writes a separate encrypted target; preserve existing plaintext source until validated recovery, second-device verification and complete byte/record comparison succeed. Never overwrite the only recoverable source.
- Stage encrypted blobs/chunks first; atomically publish the committed revision only after every referenced encrypted object is durable and verified. Interrupted staging must not become the current revision.
- Working data, attachments, backups and personal transfer artifacts need explicit coverage. Enumerate original filenames/metadata, derived thumbnails, browser caches, SQLite WAL/journals, IndexedDB, localStorage, crash dumps, downloaded exports and temporary files. Do not claim whole-app protection while plaintext paths remain.
- Preserve class/teacher permissions and all grade/record semantics above the crypto layer. Encryption is not authorization. Backup import still validates relationships after decryption.
- Unlock failures, wrong code, missing protected key or corruption must present actionable recovery UI and keep writes blocked. No silent new empty vault or plaintext fallback.
- User plaintext export, rollback and eventual plaintext retirement are explicit consequential actions; no deletion or secure-erasure guarantee follows from passing these tests.

## Evidence and sources

Fictional tests in `shared/encryption/*.test.ts` cover independent random encryptions, exact binary round trip, every context field, wrong master/app/vault, changed salt/nonce/ciphertext, old revision, malformed/duplicate/unknown formats,2MiB byte data, random recovery-code round trip/typos/wrong code, actual4MiB+3-byte chunk verification and adversarial sequence mutations.20GiB/100GiB/128GiB tests validate plans without allocating those files. Run `npx vitest run shared/encryption` and compile the shared files under strict TypeScript. This evidence does not activate encryption or prove OS/device security.

The [W3C Web Cryptography specification](https://www.w3.org/TR/webcrypto/) defines the established AES-GCM, HKDF and random-value interfaces used here (checked October29). Shared component index v10/October10 has no matching cryptography lesson; its database/packaging remedies do not validate a cryptographic design. Application-level lessons and consumer acceptance are owned by the coordinating work order rather than duplicated as authoritative shared lessons.
