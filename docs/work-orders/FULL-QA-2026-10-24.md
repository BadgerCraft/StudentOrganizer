## Severity-ranked concrete defects

P1 = high-priority correctness/authorization repair. P2 = reproducible functional/integrity defect with a narrower trigger or recoverable impact. These priorities describe this local-first app, not a remote multi-tenant vulnerability rating.

### QA-01 / P1 — an open Markbook draft silently overwrites a newer mark

**Real application Chromium reproduction.** Open existing `3+` result; perform another authorized write to `90%`, feedback `NEWER WRITE`, version 2 while the editor stays open; save the unchanged original editor. Stored result becomes `3+`, old feedback, version 3, without a conflict.

`src/components/MarkbookView.tsx:239` captures the displayed values but not their versions. `:279-300` later obtains expected versions from refreshed live-query props, pairing the old draft with the new version. The domain service's optimistic concurrency check therefore accepts a stale edit. This can replace correct grades and feedback during concurrent tabs/authorized teacher activity; audit history does not make silent replacement correct.

**Repair:** capture result and student-assessment versions (including the absent-record state) when opening the editor; retain them for save; reject/review a changed baseline. Add a real mounted/live-query stale-edit regression. Preserve the newer value on conflict. Evidence: `evidence/FULL-QA-2026-10-24/markbook-stale-repro.mjs` and `.log`.

### QA-02 / P1 — direct UI writes bypass local read-only/actor rules

**Chromium-mounted real component reproduction plus source trace.** A fictional read-only staff profile is allowed to see a class by the actual `listAccessibleClassSections` filter. It can archive that class through Dashboard; `deletedAt` changes and zero audit entries are written. It can also resize its seating layout. Profile custom-assessment creation has the same pre-authorization write problem.

Sources: `src/components/DashboardView.tsx:150-155`; `src/components/SeatingChartView.tsx:131-177`; `src/components/StudentProfileModal.tsx:219-297`; intended denial at `src/services/authHelper.ts:137`. Dashboard/seating call Dexie directly; profile commits its initial records before checking the current actor. Class archive hides the class from active views but does not erase historical records.

**Repair:** route these writes through authorized transactional services with captured actor/session identity, expected versions, audit/outbox, and allow/deny tests. UI disabling is useful but insufficient by itself. This is a bypass of the application's local teacher isolation rules, **not** evidence of remote authentication compromise. Teacher selection remains attribution rather than protection against someone controlling the OS profile. Evidence: `layout-browser.mjs/.log`, `profile-readonly-repro.mjs/.log` in the evidence directory.

### QA-03 / P2 — custom assessment failure leaves records and retry duplicates them

Related clean-install defect: `:246` and `:336` fall back to historical seed ID `rp-midterm`, whereas current initialization uses `local-reporting-period`. **Repair:** resolve a valid reporting period through the current class/term contract, normalize the selected input format before writes, and create the complete assessment/result in one authorized transaction. A retry after failure must leave exactly one complete record; every successfully created record must pass the actual backup validator. Also cover the profile override caller. Evidence: `marking-repro.mjs/.log`; supplemental grading review.

### QA-04 / P2 — restore accepts inconsistent relationships and noncanonical references

### QA-05 / P2 — supported phone work imports but cannot enter marking

**Actual codec → desktop confirmation → marking service reproduction.** Five valid fictional ~7 MiB PNG pages encode/decode successfully. Desktop import commits one attachment and receipt. `bindCaptureRoot` rejects the 35 MiB submission with “Combined image pages exceed the batch size limit”; zero partial marking attempts are created and originals remain safe.

Phone allows up to 10 × 8 MiB pages (`apps/phone-capture/src/store.ts:27,71-77`); shared capture contract lacks the per-student 32 MiB restriction (`shared/capturePackage.ts:12,39-67`). Initial desktop confirmation accepts it (`src/capture/attachmentService.ts:133-177`), but marking applies 32 MiB at `src/marking/markingService.ts:233-235` / `src/marking/validation.ts:139` / `src/marking/types.ts:32`.

**Repair:** one explicit shared admission limit, early phone/completion and desktop preflight, and a lossless remediation path for already-imported oversized work. Do not truncate/recompress originals or remove a safety validator. The fixture uses checksum-valid PNG ancillary padding to test encoded byte limits, not a claim about camera quality. Evidence: `capture-size-repro.ts`; supplemental capture report.

### QA-06 / P2 — shrinking seating hides occupied edge students

**Chromium-mounted real seating component reproduction.** A student in zero-based row 2 is visible. Reduce layout from 3 to 2 rows: the seat remains stored at row 2 but the student appears in neither grid nor unseated list. Re-expansion can recover visibility; permanent deletion was not observed.

**Repair:** block shrinking an occupied edge, or explicitly and transactionally move affected occupants to unseated with attribution. Add row/column edge regression. Evidence: `layout-browser.mjs/.log` (`EDGE_VISIBLE_BEFORE`, `READONLY_SHRINK`).

### QA-07 / P2 — organization deletion does not revoke the hierarchy guard

**Service runtime reproduction.** Soft-delete the fictional course's organization, then call `assertClassSectionWriteAccess`: access remains granted. `src/services/authHelper.ts:74-76` stops traversal on missing/deleted organization but continues evaluating its already-collected memberships. Test each role against deleted direct/ancestor organizations. Evidence: `persistence-probes.mts/.log` (`DELETED_ORG_WRITE_AUTH_ACCEPTED`).
