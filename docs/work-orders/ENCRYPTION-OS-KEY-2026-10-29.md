# Shared native protected-key provider — October 29, 2026

Status: optional injected adapter prototype and synthetic tests; no dependency installation, actual credential creation or user-device activation. Consumer applications keep separate keys while using the same scope contract. Source: `electron/platformKeyringStore.cjs`; tests: `src/security/platformKeyringStore.test.ts`. Existing Electron safeStorage integration remains supported.

## Selected implementation paths

The shared host interface is `available(): Promise<boolean>`, `load(scope): Promise<Uint8Array|null>` and `save(scope,key): Promise<{durability:string}>`. Scope is exactly `{appId,vaultId,keyVersion}` with the existing opaque identifier/version restrictions; enrollment accepts exactly 32 bytes. `null` means no enrolled credential. Locked, denied, malformed or unsupported protection rejects with a generic recovery instruction, never a plaintext fallback. `available` establishes supported configured bindings only; it is not an unlocked-keychain or successful-enrollment claim. Enrollment readback plus restart/recovery checks remain mandatory.

### Windows: nested DPAPI and local transactional storage

Use `@primno/dpapi` **2.0.1** as an optional Windows native binding. It is MIT, advertises Node >=14 and Windows x64/ARM64 N-API prebuilts, and is derived from Microsoft's Node-API DPAPI work. The published API accepts byte arrays, optional entropy and `CurrentUser`/`LocalMachine` scopes. The existing project does not need the surrounding Primno framework. Verify exact Node24 packaging and binary provenance in native CI. [Primary README](https://github.com/primno/dpapi/blob/98ab69eb35dcdd1dcf873c528906c534e566136b/README.md), [package metadata](https://github.com/primno/dpapi/blob/98ab69eb35dcdd1dcf873c528906c534e566136b/package.json).

The adapter seals a versioned, context-bound key payload with CurrentUser protection, then seals that ciphertext again with LocalMachine protection. Decode reverses the order. Both operations use a domain-separated digest of the canonical scope as additional entropy; this is public context, not another secret. Microsoft documents that CurrentUser protection can follow roaming profiles, whereas LocalMachine protection alone permits other users on that computer. Requiring both boundaries is the selected composition; it still needs independent native/security verification and does not defend against malware running as the unlocked user. [CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).

Only nested ciphertext enters a fixed local protected-key table. The host supplies `localProtectedStorage.read(scopeDigest)` and `create(scopeDigest,ciphertext)`: create must atomically reject existing entries, use bounded reads, retain the accepted row on failure, and commit with the reviewed SQLite durability settings. Callers supply a trusted profile-wide exclusive lock covering all processes and the complete save/readback operation. Do not substitute a JavaScript promise queue for cross-process exclusion. Missing lock/storage/binding disables this adapter; there is no boolean attestation that pretends to implement the native operations.

Do not use Windows Credential Manager for this protocol. The examined keyring backend defaults to Enterprise persistence, and its JavaScript wrapper does not expose the required local persistence modifier. Avoiding that provider also avoids implicit credential roaming. [Backend persistence documentation](https://docs.rs/windows-native-keyring-store/latest/windows_native_keyring_store/).

### Mac: native login Keychain

Use `@napi-rs/keyring` **2.1.2**, MIT, maintained in `Brooooooklyn/keyring-node`, with x64/ARM64 Mac prebuilts. Node-API compatibility makes a Node24 host feasible; actual packaged loading is still a native-CI check. The upstream build uses locked Rust dependencies and ships third-party notices. [Pinned package/source](https://github.com/Brooooooklyn/keyring-node/tree/81c00e607281f1b13959d48cbbb1998ce0421df9), [license](https://github.com/Brooooooklyn/keyring-node/blob/81c00e607281f1b13959d48cbbb1998ce0421df9/LICENSE).

Use `new AsyncEntry(service,account)` and `getSecret`/`setSecret`. The service and account contain only domain-separated scope digests; the stored payload independently binds the full scope. Only absence returns null; inaccessible/locked keychain errors reject. Do not enumerate unrelated credentials. The examined Mac backend selects the file-based User/login Keychain and its generic-password API, rather than requesting synchronizable protected-data storage. This source-path finding does not prove actual user Keychain settings, hardware binding or protection against manual keychain copying. [Binding selection](https://github.com/Brooooooklyn/keyring-node/blob/81c00e607281f1b13959d48cbbb1998ce0421df9/src/entry_builder.rs), [Mac backend](https://docs.rs/apple-native-keyring-store/latest/src/apple_native_keyring_store/keychain.rs.html).

Never use `withTarget` as a general read helper: the examined Windows binding's constructor writes an empty secret in that path. The adapter does not call it. Mac enrollment requires the same trusted cross-process profile lock, checks for an existing key, accepts an identical key idempotently and rejects a different key. The OS keyring API itself is not a compare-and-swap primitive. Manual/outside modification by programs with the same user's authority remains outside that lock's guarantee.

## Key lifetime and failures

Copy enrollment bytes before the first await and best-effort wipe owned buffers when finished. Context/version and exact decoded key length are validated after protection is removed. Native exceptions, key payloads and provider response text never enter logs, shell arguments, environment variables, browser responses or AI prompts. No shell-based keychain commands are used. JavaScript strings/runtime internals cannot be guaranteed erased; do not claim otherwise.

After a native write is attempted, a rejected response or failed readback yields `DEVICE_KEY_SAVE_UNCERTAIN`. Inspect/reopen the enrolled entry under the profile lock; do not automatically overwrite or delete it. The adapter deliberately exposes no deletion/rotation path. Successful `os-store-readback` is not proof of power-loss persistence; conversion still requires separately verified offline recovery, independent second-device enrollment and restarted unlock.

Optional bindings load only when explicitly configured on supported Windows/Mac platforms. Linux is rejected, including weak/in-memory fallback backends. No account, service, grant, paid component, new repository or framework is required for these local bindings. Consumer dependency changes and packaged runtime tests belong in their existing repository.

## Local transactional key registry implementation

`electron/sqliteProtectedKeyStore.cjs` implements the protected-storage/profile-lock dependency, using Node24's builtin SQLite without another native dependency. Construction receives a trusted fixed directory and scope; the only filename is `profile-keys.sqlite`. `withExclusiveProfileLock(fn)` holds a `BEGIN IMMEDIATE` transaction with a1000ms busy timeout on one connection. `read(slot)` and `create(slot,alreadyProtectedBytes)` require the current live AsyncLocalStorage lease on that same connection. Do not open another connection inside the callback. Nested calls reject. Unrelated async chains have no lease; descendants cannot reuse it after callback completion. Errors are generic and never SQL bound values.

The STRICT table primary key is `(app_id,vault_id,key_version,slot)`. Values are bounded nonempty OS-protected BLOBs only; the registry does not authenticate encryption or accept plaintext as a substitute for the host's OS-protection step. Create is exclusive and never overwrites an enrolled row. SQLite schema/application/version are fully attested, WAL/FULL synchronization is required and temporary SQL work stays in memory. Initial schema enrollment commits separately so an interrupted first key transaction can be safely retried. A rolled-back schema transaction leaves only a recognizable empty SQLite file which enrollment can retry without deletion. Commit acknowledgement loss is reported as `PROTECTED_KEY_COMMIT_UNCERTAIN`; reopen the actual row before deciding a retry.

Use a fixed trusted device-profile scope/slot for an OS-wrapped random device identifier, independent of copied vault metadata. Use the actual app/vault/key-version scope for each wrapped master. A foreign copied OS-wrapped identity must fail closed; do not regenerate it silently or adopt a renderer-provided identifier. A supported second computer begins with its own fresh protected profile and enrolls through verified recovery/transfer.

Ten real-filesystem synthetic registry tests pass, in addition to the nine OS-adapter mock tests. They cover scoped create/reopen, exclusive replacement rejection, complete rollback, failed initial schema retry, active/expired/unrelated async leases, committed reply loss, full-schema corruption rejection, size/input bounds, independent-process competing create, bounded cross-process lock failure, and abrupt process exit after row creation before COMMIT. OS API behavior and physical power-loss guarantees remain separate from these actual NodeSQLite tests.


Published artifact API verification: downloaded the2.1.2 npm tarball with lifecycle scripts disabled (no dependency installation or native calls). Its `package/index.d.ts` declares AsyncEntry.setSecret(Uint8Array) and getSecret():Promise<Array<number>|null>. Node Buffer is a Uint8Array and is the correct write boundary; converting writes to a plain Array would violate this API. Both mocks now reject non-Uint8Array writes. Version2.0.8 was not present in the queried registry; it is not an approved substitute for the pinned2.1.2 artifact.


## StudentOrganizer main-process assembly

`electron/encryptionProfile.cjs` binds an independent device seed and vault master to native protected storage; it exposes the actual SQLite profile lease to the head protocol. `electron/encryptionNativeRuntime.cjs` assembles profile, OS head, staged SQLite checkpoint storage and chunk providers around the main-owned host. A fresh legacy launch/preparation performs no persistent enrollment or OS-key query. Default activation is false. Protected metadata is only a selector: the OS-derived device identity must match, and authenticated data plus the independent head establish the usable checkpoint. Missing/corrupt protected material stays locked rather than choosing the legacy database.

Initial publication requires the private `withFreshEnrollment(assertCurrent,action)` capability or the host's main-only synchronous preparation assertion. The host owns the actual recovery/second-device verification; a renderer cannot install the capability. Runtime lock invalidates it. Recovery enrollment authenticates the master wrapper and challenge before adopting a source vault scope, and persists only the encrypted wrapper/response. Initialized metadata with no checkpoint remains enrollment-pending, not an unlocked empty workspace.

Explicit receiver cancellation is permitted only for known pending metadata with no checkpoint and no unresolved/head-bearing OS receipt. It preserves all pending encrypted/OS material and permits a legacy return in RAM for the current process only; restart returns to the pending secure flow. Future refresh rechecks the empty-head condition. It never deletes keys or resets an existing protected head. This is an explicit user-directed rollback boundary, not an automatic plaintext fallback.

Six assembly tests use real local SQLite with synthetic injected OS providers. They verify zero-artifact legacy preparation, default-denied enrollment, ciphertext publication/reopen, missing OS-head rejection, corrupt-artifact lockdown, capability revocation with a valid ciphertext, and pending-cancellation/restart behavior. They do not establish real Keychain/DPAPI acceptance or the complete structured-host/UI workflow; those are owned by the coordinating native integration and independent review.
