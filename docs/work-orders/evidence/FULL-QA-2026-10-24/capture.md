## Concrete defect

### CAP-01 — P2: a supported completed phone page set can be imported successfully but cannot be marked

- Phone allows 10 pages at 8 MiB each with only a 256 MiB whole-assignment limit (`apps/phone-capture/src/store.ts:27`, `:71-77`); shared manifest has no per-submission 32 MiB rule (`shared/capturePackage.ts:12`, `:39-67`). Completion validates the exported ZIP before freezing (`apps/phone-capture/src/main.ts:117`).
- Initial desktop capture confirmation also accepts the set (`src/capture/attachmentService.ts:133-177`); only the *append* branch checks 32 MiB at line 166.
- Start marking calls `MarkingService.bindCaptureRoot`, assembles all original pages and validates at `src/marking/markingService.ts:233-235`. `assertMarkingImagePages` rejects above 32 MiB (`src/marking/validation.ts:139`, configured in `src/marking/types.ts:32`).
- Runtime reproduction: `/tmp/studentorganizer-review/capture-size-repro.ts`. Five valid one-pixel PNGs each padded with a checksum-valid 7 MiB ancillary chunk exercise the same encoded-byte budget as camera photographs. Shared encode and decode pass; actual `CaptureAttachmentService.confirm` writes one attachment and one receipt; actual `bindCaptureRoot` fails with `ValidationError: Combined image pages exceed the batch size limit.` It leaves zero marking attempts (safe rollback). Output: ZIP 36,702,875 bytes; originals 36,700,510 bytes; attachmentCount=1; receiptCount=1.
- Impact: teacher can complete/freeze, transfer and match otherwise-supported work before discovering it cannot enter the grading workflow. Originals remain safe; this is workflow failure, not demonstrated data loss or incorrect marks. Real photos of five >6.4 MiB pages suffice.
- Repair: choose one explicit shared per-submission capacity contract. Safest bounded change is an early phone admission/completion check and clear actionable message, plus matching desktop intake preflight. Existing oversize attachments need an explicit lossless splitting/remediation path; do not silently truncate or recompress originals. Add full export→decode→confirm→bind threshold regression, including boundary and overflow. Raising desktop limits requires capacity/memory/backup validation rather than removing a validator.

## Justified architectural improvements

### CAP-A01 — shared media layer depends upward on desktop document parser and root installs

`shared/capturePackage.ts:2` and `shared/capturePreview.ts:1` import `src/marking/importImages`; phone imports it directly too (`apps/phone-capture/src/main.ts:4`). The image module imports SHA-256 from `src/marking/importDocuments.ts` (`src/marking/importImages.ts:2`), which imports saxes and references Mammoth. This is real dependency inversion: phone image packaging typechecks through the desktop DOCX stack and root package installation. Phone package declares dexie/fflate but not those document-parser dependencies. Android README's phone-only `npm ci --ignore-scripts && npm run build` instruction assumes root dependencies already exist.

Disposable clean-layout check `/tmp/studentorganizer-review/phone-clean/` copies the transitive production sources with only the successfully installed phone node_modules. `tsc --noEmit` fails to resolve fflate from shared/root source, saxes and mammoth; evidence `/tmp/studentorganizer-review/phone-clean-build.log`. Full monorepo installation succeeds, so this is not a current root build failure. Extract neutral byte hashing/image validation/geometry into a shared package with explicit dependency ownership, or immediately document root installation as a prerequisite. Preserve shared behavior instead of copying implementations. A clean-install build CI job is the acceptance check.

### CAP-A02 — duplicated parser policies need differential contract tests, not a speculative rewrite

`shared/capturePackage.ts` and Android `CaptureQueue.java` separately enforce the capture package schema, ZIP framing, hashes, image bounds and crop coordinates. `src/marking/importDocumentArchive.ts` and `importDocuments.ts` each own distinct ZIP policies as well. The formats differ intentionally (DOCX support versus narrow capture format), so indiscriminate consolidation would be risky. Keep the native boundary independently defensive, but maintain a shared corpus of valid/invalid packages run against browser and Java validators. That catches threshold/version drift such as CAP-01 without weakening either trust boundary. No current malicious-package bypass was demonstrated.

## Strong paths traced

- Phone writes use a Dexie transaction, optimistic revisions and immutable completed identities (`store.ts:34-49`); late-work identity/reuse is transactionally selected (`:53-68`). Recovered camera photos dedup by durable ID and are acknowledged only after persistence (`main.ts:104-107`, `:143-160`). UI async actions are serialized and preserve failed input (`:94-100`).
- Capture parser inspects central/local ZIP header agreement, contiguous nonoverlapping ranges, normalized paths, declared and actual decompression size, CRC, cryptographic page hashes and valid image bytes before import (`shared/capturePackage.ts:76-181`). Labels never become roster identity automatically.
- Confirmation snapshots caller data before async validation, rechecks actor and class enrollment inside the write transaction, uses durable teacher/assessment/package/submission receipts and rejects changed-content retries (`attachmentService.ts:133-178`). Explicit append updates are in the same transaction as attachment and receipt creation. Wrong actor, old draft version, finalization, archive and backup-capacity boundaries remain protected by marking service.
- Attempted backup-capacity finding was disproved: despite original duplication into marking attempts, binding invokes `assertCaptureBackupCapacity` at `markingService.ts:250`, and append at `:287`; do not report it as a defect.
- Android transfer persists generated folder/file IDs before network creation, verifies existing remote metadata on retry, checks ownership/privacy/location and hashes before COMPLETE, and preserves local originals (`TransferEngine.java:20-132`). Endpoint/session URL restrictions and disabled redirects are in `HttpDriveGateway.java:117-150`. Worker state is serialized, retry-aware and tied to the selected account/explicit per-process enabled setting (`TransferWorker.java`).
- Android renderer only loads bundled appassets GET resources; navigation and other network resources are blocked; no file access, debug WebView, cleartext or OS backup (`MainActivity.java:45-67`, AndroidManifest.xml:5). OAuth tokens remain native; Java bridge validates package metadata independently. This is static source evidence, not physical-device certification.
- DOCX validates bounded archive expansion, CRC, XML depth/count, forbids external relationships/embedded executable parts, and reconstructs the verified archive before the browser Mammoth parser (`importDocuments.ts:46-153`). TXT uses strict UTF-8 and control/text size checks. Class ZIP validates every outer entry before parsing documents and reports per-document recoverable errors (`importDocumentArchive.ts:126-151`). No external text/image URL fetch is used by these import paths.
