## Substantive architecture assessment

The marking subsystem has a sound core; a rewrite is unwarranted. Its strongest path is import → immutable confirmed rubric → student-matched attempt → versioned session/draft → explicit category judgments → transactional finalization → existing markbook service → immutable receipt/report. `MarkingService.transaction` (:28–44) checks active actor/epoch and device and aborts on teacher changes; context links class, unit, reporting period and enrollment. `baseline` (:103–111) captures actual official results, policy and scale values so silent legacy writes are detected. `finalize` (:402–460) checks category snapshots, pending feedback, official baseline, missing/excused status and old assessed results, and runs all category writes plus receipt in one transaction. Retry returns the existing receipt. Rubric labels/reference weights remain evidence; no automatic averaging substitutes for deliberate KTCA judgments.

Grading math is centralized in `services/calculationEngine.ts`: normalize input, aggregate weighted evidence independently per category, then apply class category weights; observations do not enter this path. Classroom level mappings are explicit immutable values in `classroomLevels.ts`; direct percentage stays direct. Different legacy scale_code and classroom_level mappings are intentional, not duplicate bugs. Markbook, profile and CSV use the same calculation function.

Archive is deliberate records management (`MarkingService.archiveAttempt` :471–527): teacher/ownership/version checked; finalized receipt drafts retained, unfinished sessions discarded; source bytes/quotes/drawing coordinates removed when Keep work off; audit/outbox payloads redacted too. Official grades are untouched; archived attempts reject future writes. Existing archive/category-recovery suites contain meaningful failure and preservation assertions (coordinator executes). Import uses local bounded DOCX parsing, validates archive/external-resource restrictions, and requires human rubric mapping. Reports escape content and disallow script/network resources.

The central architectural weakness is uneven adoption of these boundaries. Older profile direct database writes bypass validation/authorization/audit and split a user operation across commits, whereas newer marking code has a proper atomic service. Fix concrete remaining write paths before broad component refactors. Also use one shared policy/period resolver: MarkingService.scaleOptions and both MarkbookDomainService entry points duplicate fallback selection; App.activePolicy simply takes first policy without deleted/default scoping (`App.tsx:316`). This is a justified consistency improvement, not independently reproduced incorrect grading beyond M3.

MarkingService takes all database tables for every transaction (`:30`), making correctness simple but serializing unrelated work and complicating component isolation. Large history redaction scans all audit and sync rows (`:516–523`). These warrant measured table scoping/indexing after correctness fixes, not speculative rewrite. Domain validation imports ValidationError from persistence-heavy markbookService; a small shared errors module would clarify dependency direction if editing those contracts anyway. No unused-file deletion or cosmetic UI overhaul is recommended.
