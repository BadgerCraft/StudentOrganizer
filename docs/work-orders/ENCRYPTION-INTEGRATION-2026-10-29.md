# Student Organizer encryption integration — staged implementation

Authority: Tyler approved encrypted working data, backups and personal-computer transfers, independent per-app keys, trusted-device automatic unlock and an offline recovery code. Development uses fictional data and synthetic keys. Actual user activation, credential provisioning, real-device enrollment acceptance and any new PR merge/release/deployment remain separate.

## Stage 1: implemented substrate

`src/security/encryptedWorkspace.ts` integrates the shared `shared/encryption` contract into a memory-only workspace session. It is not enabled in the existing App and does not relabel persistent Dexie storage as encrypted.

- `EncryptedWorkspaceStore` reads an encrypted checkpoint and atomically compare-and-swaps a new revision. Native implementation owns fixed paths, durable writes and access checks. Commit must resolve only after durable success.
- `EncryptedWorkspaceSession.open` authenticates and validates the encrypted workspace before exposing a defensive memory copy. It never accepts plaintext or falls back to existing storage.
- `transact` serializes edits, validates an isolated candidate, encrypts it and commits before publishing/acknowledging the new state. Caller references and key/scope mutations cannot alter committed state. Reads during pending writes retain the preceding committed state.
- A stale/failed/uncertain commit locks and clears the session. Queued edits do not replay. Reopening reads/authenticates the actual durable revision; an upload/write reply lost after commit does not cause an automatic repeat.
- Encrypted backup and transfer exports use separate authenticated purposes and caller-provided non-sensitive stable identities. No grade conversions or authority rules are introduced.
- `WorkspaceMigration` requires actual recovery-code unwrap/key comparison and a fresh distinct-device possession challenge response. Boolean acknowledgments cannot satisfy either check. An old challenge or wrong device identity is rejected. These proofs establish key possession, not that a second physical computer has passed native acceptance.
- Conversion rechecks the complete source digest while the consumer holds an all-writer read lock and writes a new target only. It never modifies/deletes the source. Existing encrypted targets cannot be overwritten. Failed/uncertain conversion closes the ceremony; resume by inspecting the durable target rather than replaying writes.

The source adapter contract must freeze **every** source writer for capture and conversion, including both databases and local comment banks. A normal Dexie transaction does not freeze localStorage or a separate recovery database. There is deliberately no default adapter claiming this protection.

## Next-stage transaction architecture and disposable proof (October 29)

A disposable prototype against the installed Dexie 4.4.6 runtime is at `/tmp/dexie-encrypted-boundary-proof.mts` (log beside it). It does not modify production code. It establishes a technically viable preservation path for current Dexie query/service behavior:

1. Use one coordinator across the in-memory primary and recovery Dexie instances. Gate every root implicit `Table._trans` and explicit `db._transaction` entry, including reads, before creating an IDB transaction. Matching nested operations retain the existing transaction/rollback semantics. Gate comment-bank and private freeform draft storage through explicit asynchronous adapters too; synchronous `localStorage.setItem` cannot acknowledge a durable encrypted save.
2. Disable Dexie's optimistic cache (`cache: 'disabled'`). Otherwise a query may receive optimistic writes before durable acceptance. The prototype intercepts root `_createTransaction` completion, waits for the encrypted full-bundle commit, then resolves the original operation. It suppresses native `mutatedParts` notification and re-emits `Dexie.on.storagemutated` only after persistence. This uses internal APIs and requires pinning/auditing the exact installed Dexie release; a dependency upgrade must fail the acceptance suite until reviewed.
3. While the coordinator owns the boundary, collect the just-completed RAM state via a private raw read-only backend transaction, bypassing the public gate to avoid deadlock. All ordinary readers/writers stay queued. Include primary/recovery/application-owned local state in one encrypted authoritative bundle. Do not emit live-query updates or show saved success until native durable CAS returns.
4. A failed or uncertain CAS locks every reader/writer and unmounts classroom UI. The RAM transaction may already have completed, so pretending it rolled back is incorrect. Reopen authenticated authoritative bytes to determine the actual committed state. Do not replay the queued write. All UI context changes, logout, vault close and actor epochs must be coordinated/fenced through this same boundary; a revocation after the disk linearization point cannot retroactively make a confirmed write disappear.

**Observed prototype checks:** implicit add; nested explicit transactions; reads and write acknowledgment blocked during delayed persistence; liveQuery does not emit pending state and updates after acceptance; several mutations then abort produce no vault commit and restore RAM records; collection modify/delete; failed CAS blocks later reads and leaves the prior synthetic durable snapshot. Fake IndexedDB and a synthetic commit callback are used. No real data, keychain, OS activation or production adapter is involved.

**Not yet proved:** multiple databases under one coordinator; all application storage writers; `rw!`/`rw?` forced nesting; schema upgrades; close/identity interruption; async mutator `Dexie.waitFor` and cancellation; autosave races; actual native partition/restart; renderer crashes during the encrypted commit; complete source collection and native authority checks. These are implementation acceptance gates, not a request to weaken the full scope. Do not ship the prototype hooks based only on the successful subset.

### Complete source and launch contract

The collector must run only after `assertWorkspaceAccess(database, userId, capturedEpoch)` and repeat that check after all bytes are captured, while the coordinator freezes all writers. It must include every primary table and inline attachment/source byte, recovery backup/options/sync-base tables, every authorized teacher comment bank and relevant app-owned private drafts/hints. The existing full-backup validator covers primary records and bytes, but it does not automatically cover separate recovery/localStorage stores. Retained foreign teachers and archived classes keep their current authorization boundary. Source autosave/automatic backups must not race migration. Do not load private values into AI logs or write plaintext migration staging files.

At native launch, read an unambiguous protected mode selector before constructing a classroom window. Legacy mode continues with the preserved source partition until explicit conversion acceptance. Encrypted mode creates a fresh **nonpersistent** partition, disables disk cache/persistent service workers, mounts only the locked bootstrap, unlocks the app-specific OS key, authenticates/validates the full bundle and hydrates the RAM databases. Only then dynamically import `App`/the Dexie singleton. A protected-mode unlock/authentication error must never mount legacy App as fallback. Startup and migration preserve the original source; changing back must be an explicit rollback with its stale-data implications.

### Backup, transfer and readable PDF behavior

Encrypted-mode recovery snapshots and sync ancestry live inside the encrypted bundle. Native Drive upload/download must accept bounded authenticated backup/transfer containers and retain existing private-owner/immutable-version checks. Decrypt before existing relational merge validation; encrypt the resulting bytes before transmission. The current JSON Drive parser is insufficient and must not be reused as though encrypted bytes were supported. Repeated/uncertain transfers retain existing refresh/review behavior.

Readable PDF/CSV reports are intentional user-selected exports outside vault protection; keep existing report bytes and grading semantics. The save action must make readable output explicit. The existing PDF exporter uses a scriptless nonpersistent print window and a private same-directory plaintext staging file before atomic rename. In encrypted mode this staging belongs to that explicit readable export; restrictive permissions, cancellation cleanup and cleanup-failure notification are required. It is not an encrypted backup or a hidden working-data cache. Historical exports/source files, OS swap/crash dumps and forensic erasure are not protected merely by encrypting the workspace.


## Stage 2 storage-boundary candidate — separate worktree

Branch `codex/encryption-so-storage-gate-20261029` is based on reviewed foundation `8a2d0df`; its files are isolated from the foundation CI branch. No actual App activation or key provisioning is added.

`durableDexieGate.ts` implements the pinned Dexie 4.4.6 coordinator. Registration rejects unsafe cache configurations or mixed runtime constructors. Root implicit/explicit reads and writes serialize across registered RAM databases; matching nested transactions preserve rollback; forced/fallback nesting, escaped transaction tables, independent ignored roots and cross-database nested transactions fail before independent writes. The adapter captures caller authority before queueing, rechecks before persistence and acknowledgment, and passes a required assertion to the persistence callback for immediately-before-CAS checks. Context changes use `contextBoundary`, while immediate revocation locks all pending/queued access. Native mutations may have completed in RAM before persistence: a failed/uncertain durable outcome locks the session rather than claiming rollback. Completion hooks, saved acknowledgment and reactive notification wait for accepted persistence.

The first candidate's privileged PSD inspection flag was rejected after its own read-blocking test exposed a read of an undurable RAM revision. The final architecture grants **no read bypass capability**: it captures detached values through private raw IDB read-only transactions and passes those values to persistence/source callbacks. Those callbacks must not query the live registered databases. All ordinary readers queue behind persistence. This removes both active async-continuation and late-callback inspection escapes. Snapshot values are detached; callback access does not expose a live database handle.

`studentOrganizerSource.ts` builds a typed complete working bundle from the captured values. It checks exact primary/recovery table sets, preserves device/preferences/outbox records, validates inline byte-bearing work, includes all dated recovery versions/base/options and authorized app-owned comments/private draft/hints, and rejects unknown storage keys. `ontario_active_user_id` is not accepted as a durable localStorage hint; hydration must always require explicit teacher confirmation. The existing `assertWorkspaceAccess` runs against detached in-memory inspection databases before/after capture and against **each retained backup/base**, so foreign-teacher history absent from the current DB cannot bypass the shared-workspace boundary. Embedded marking/capture bytes are validated in primary, backups and sync base. Existing source data is unchanged.

The inspection database uses the already installed `fake-indexeddb` implementation strictly to avoid creating a plaintext inspection store on disk. It does not claim that a fake database constitutes protected durable storage. Packaging must retain this dependency or replace the isolated validator with equivalently complete pure validation; do not redirect inspection to the persistent browser default.

Verified: 17 focused unit tests across gate/source files; strict TypeScript; actual Chromium through Vite's browser ESM dependency resolution. Browser checks observe old committed state while CAS is held, block both write acknowledgment and a concurrent read, publish live-query results after durable acceptance, reject forced nested roots atomically and preserve collection writes. Unit coverage additionally includes actual SO seeded schemas, full bundle encryption/restart with inline photo and retained recovery/comments, foreign-teacher content only inside backup/base, context changes, queued authority, close, late captured callbacks, multiple databases/external memory writes, multi-write abort and `Dexie.waitFor` async mutation. Evidence: `/tmp/durable-source-tests.log`, `/tmp/durable-gate-types-final.log`, `/tmp/durable-dexie-browser-proof.mts` and `.log`. Independent reviewer has been notified; fixes and bounded results must be reviewed before publication.

### Remaining integration gates

The storage coordinator is a substrate, not automatic coverage of current App. Actual startup must create disabled-cache memory stores before hydration and register every DB; existing synchronous comment-bank/private draft writers need async coordinator adapters. Source capture callbacks must read only the memory storage adapter whose writers use the same coordinator. Legacy localStorage copied outside that boundary must never be described as frozen merely because the callback has a convenient name. Complete native startup, UI/writer wiring, autosave and context transitions, report/export disclosure, Drive container integration, actual native OS acceptance and second physical computer verification remain required before enabling conversion. Recovery proof and enrollment possession proof remain separate from physical-device acceptance.
