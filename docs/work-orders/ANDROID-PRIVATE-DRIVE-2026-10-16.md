## Controllable data path

Packaged local WebView assets → local capture IndexedDB → deterministic ZIP snapshot → native bridge → immutable internal ZIP + SQLite queue → native WorkManager → native AuthorizationClient → direct HTTPS Google Drive API. No app backend, AI/model/OCR call, assistant relay, analytics, remote renderer scripts or public-link creation. Google is the authorized storage recipient; this is not a claim that Google's storage/security infrastructure never uses automation. Build/review tools see source code and fictional fixtures only.

The native WebView loads only packaged `https://appassets.androidplatform.net/assets/` resources, blocks navigation and unapproved requests, disables debugging, and never receives OAuth tokens. Native networking pins the Google Drive HTTPS host/path, refuses redirects and retains tokens only for the current native operation. Android backup/data extraction is excluded. The camera and photo import use native system intents; local export requests a document destination. Use only the approved phone/computer/private Drive destinations.

The only requested Google scope is `https://www.googleapis.com/auth/drive.file`. An explicit foreground account choice and authorization bind the queue to Drive's account permission ID. Automatic upload defaults off; Wi-Fi/unmetered only defaults on and is visible/editable. Enabling transfer authorizes creation of `StudentOrganizer Capture (private)` in that user's My Drive root. The worker persists the generated folder ID before creation; no existing assistant-known folder ID is treated as app authorization. Ownership, complete permission listing, parent/root and shared/trashed state are checked. Unknown/shared/moved destinations block; no permissions are changed to repair them.

Only saved, fully-labelled batches autoqueue after opt-in. Each capture/revision is an immutable snapshot; later edits create another revision rather than silently overwriting an uploaded copy. Fixed ZIP timestamps make the same revision's bytes deterministic across retry/restart. Stable generated Drive file IDs are saved before upload initiation, resumable session URLs are persisted, and a retry/409 checks the existing file rather than creating a duplicate. Completion requires expected parent, ownership/permissions, byte length, MD5 and SHA-256. Local originals are never automatically deleted. Quota/permission/auth problems retain records and expose a blocked/reconnect state; network/rate limits retry with backoff.

Opt-out stops scheduling/new requests/chunks; it cannot retract an already in-flight request. Privacy checks cannot atomically lock Drive sharing against an external user changing permissions mid-request; checks before/after upload detect changes and do not claim a verified private copy. WorkManager retries while this process has explicit transfer consent, not instant delivery or a tested device guarantee. The October17 safety repair requires explicit re-enable after process restart; the durable queue is retained, but restart alone cannot resume delivery. Google Drive for desktop can deliver the ZIP to the computer using the user's own setup; **desktop extraction, grouping/import and explicit student matching remain manual**. No manifest importer or automatic desktop ingestion was added.

Safety decision: a completely failed disk cannot durably record a requested pause. A memory-only stop flag alone would also disappear on restart. The bounded repair therefore retains durable queued files/configuration but scopes upload consent to the current process, requiring explicit enable after every process restart. This sacrifices unattended restart delivery to prevent stale persisted consent authorizing transfer. No new product/account authorization is inferred.

Implementation: `TransferSettings` owns the sole production SharedPreferences adapter, a copied committed snapshot, a transient consent permit and callback generation. Only a successful complete commit publishes new account/folder/Wi-Fi/notice state. False/throwing writes lock out further changes and requests for that process; dirty preference memory is never reread. Successful writes persist `enabled=false`, neutralizing legacy consent. Callback invalidation needs no disk write. UI enable/reconnect/revoke actions do not continue after unsuccessful settings saves; failed Wi-Fi controls return to their committed value. A retry queue write exception pauses transfer and reports retained originals rather than crashing or scheduling another run.
