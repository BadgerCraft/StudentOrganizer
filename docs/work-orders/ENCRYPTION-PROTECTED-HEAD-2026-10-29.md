# Independent protected revision head and pending receipts — October 29

Implementation: `electron/protectedRevisionLedger.cjs`, `electron/pendingEncryptedCommit.cjs`, and `native/windowsCredentialLedger.cc`. These are shared Node/Electron host components; no renderer key or arbitrary native credential API is exposed. Their separate filesystem and OS-key providers remain explicit host dependencies. No real-device provisioning or activation was performed.

## Windows API path

The small Node-API addon calls `CredReadW`/`CredWriteW` for a generic credential with **CRED_PERSIST_LOCAL_MACHINE**, using a fixed-purpose opaque target derived from the app/vault/key-version scope. This persistence constant retains a credential across logons on this computer; it is different from DPAPI's `CRYPTPROTECT_LOCAL_MACHINE` encryption flag. It does not request Enterprise roaming. Reads attest the returned persistence/type and reject inaccessible or malformed entries; only `ERROR_NOT_FOUND` means absence. [CREDENTIALW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw), [CredReadW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw), [CredWriteW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credwritew).

The addon uses the established Node-API C interface and Windows Advapi32, not new cryptography or a service. It bounds targets to the exact protocol prefix plus a64-character lowercase digest, rejects embedded NUL/other spellings, and accepts at most2048 receipt bytes. No master key or recovery code belongs in the ledger. Native errors are generic. There is no production deletion export: `removeSynthetic` accepts only the isolated `TeacherVaultLedgerQAV1-` namespace used for synthetic native CI metadata.

`scripts/buildWindowsCredentialLedger.cjs` builds the binding with the existing Node-gyp toolchain and copies it into `electron/generated`. `scripts/windowsCredentialLedgerSmoke.cjs` performs a scoped synthetic receipt read/write and removes its QA entry in `finally`. Run both only on an authorized Windows QA runner. Source/mock checks do not establish actual Windows runtime availability; a missing build/binding blocks protected operation.

Mac uses the reviewed native login Keychain `AsyncEntry` API for the same bounded canonical receipt. No default Windows NAPI keyring provider is substituted: its default Enterprise persistence and unsafe `withTarget` constructor path are excluded. Neither provider is an OS-level atomic compare-and-swap primitive; all cooperating processes must hold the actual profile SQLite lease across read/expected comparison/write/readback. The ledger requires a synchronous `assertProfileLease()` that throws outside the live lease; a promise or boolean attestation is rejected.

## Receipt and commit contract

An OS ledger record contains version, full scope, `head:{revision,hash}|null`, and `pending:null|{operationId,base,next}`. Base/next contain only a revision and SHA256 of the **exact UTF-8 ciphertext bytes**. Canonical parsing rejects unknown, duplicate, alternate-context or oversized receipt encodings. Pending base equals the current head; pending next is exactly one revision above it. The native credential is independent of copied workspace files.

`createPendingEncryptedCommit({scope,withExclusiveProfileLock,ledger,candidates})` returns `commit(expectedHead,nextCheckpoint)` and `reconcile()`. The candidate store provides `stage(operationId,checkpoint)`, `readStaged(operationId)`, `publish(operationId,baseHead,checkpoint)` and `current()`. It must durably stage encrypted bytes, enforce publication against the expected current head, and never stage plaintext. Domain validation and authenticated decryption remain separate mandatory steps; a SHA256 match alone does not authenticate student work.

Commit stages exact encrypted candidate bytes and reads them back before installing a protected pending receipt. Only then may it publish the candidate. It checks the published exact hash, then replaces the receipt with the new protected head. Responses are `durable`, `rejected` or `uncertain`; no automatic retry occurs. Staging or readback I/O failures are conservatively uncertain even before a protected receipt attempt: a failed storage response cannot establish that the pointer or database stayed unchanged. Known-invalid input, stale expected heads and missing verified enrollment are rejected before staging. An unresolvable existing receipt or failure after a pending attempt is uncertain and blocks normal writes pending reconciliation.

Restart reconciliation accepts only the exact candidate identified by the durable receipt's operation/revision/hash. If current matches pending next, it completes the head update. If current matches pending base, it may publish only the matching staged candidate. An unmatched candidate, missing candidate, unexpected revision, changed bytes or workspace/head mismatch remains blocked. Without a pending receipt, the current workspace must match the protected head. The OS ledger CAS itself permits only identical idempotence, initial empty/first pending enrollment, stable→bound pending and pending→its exact next head. Rewind, skip, same-revision hash substitution and pending-operation replacement are rejected. UUIDv4 operation identifiers are strict. Historical recovery has no reset API: recovered historical work must be validated and re-encrypted as a new current revision.

## Threat boundary and evidence

This detects rollback of workspace files relative to the independently retained OS head. It cannot detect restoration of both the entire OS credential state and matching workspace/ledger state to an older consistent point. Hardware monotonic counters or an external trusted service would be needed for that stronger guarantee; none is claimed or introduced. Same-user malware and an unlocked compromised process are also outside the at-rest guarantee. OS account/profile restoration and manual Keychain copying are explicit limits.

Synthetic tests cover receipt scope/canonical bounds, native-provider absence, lease assertions, exact CAS, matching versus substituted staged ciphertext, old workspace revision, historical restore as a new revision, and interruption after pending receipt/publication/head updates. Existing actual SQLite lease tests cover competing processes and expired/unrelated async contexts. Windows compilation/native receipt tests and end-to-end production publication integration must pass before activation. No real master/recovery secret is used by the native smoke test.


Fresh enrollment policy: A missing OS ledger or an enrolled null protected head plus empty current storage returns `enrollment-required`, never a normal unlocked durable workspace. Initial commit requires a synchronous trusted `assertFreshEnrollment()` capability, checked before staging and again before writing the first receipt; it must verify the host's actual prepared activation, offline recovery and second-device ceremony. The default rejects. It is not a checkbox, renderer assertion or always-true production callback. Missing OS state on an established workspace always blocks normal unlock; these primitives never create an empty fallback.

Final review corrections: CAS transition-reset and expired-lease gaps were reproduced and repaired. The ledger checks its live lease before and after OS reads/writes. Seventeen focused ledger/coordinator tests pass, including stage-corrupt/current-unreadable classification, forbidden rewinds/skips, strict UUIDs, expired-read zero-write checks and explicit enrollment gating. Native Windows compilation/probe remains a separate required check.
